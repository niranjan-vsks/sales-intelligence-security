# P8: Prospect report card (deterministic card, LLM explanations, faithfulness-checked)

Model: Sonnet 5.5 for the build. Generation runs on the `mid` tier of
the gateway, the judge on the `reasoning` tier; the loader asserts the
two tiers' primary models are different families so the judge is not
grading its own output. Day 5, first half.

## Goal

When a salesperson clicks "Mark prospect", the app produces a report card
for that account: our findings, our evidence, the peer comparison, and 2
plain sentences per finding written by an LLM from our evidence only,
rejected automatically if they say anything the evidence does not. Cost
per card logged. Judge-evaluated on 50, human-calibrated on 30. Rendered
as an HTML page and downloadable as PDF-ready HTML (print stylesheet).

## Read first

DESIGN.md section 7.2 and 11. DATA_MODEL.md sections 5.2 and 5.3. P7's
`sis/llm/gateway.py` (reuse; do not write a second client).

## Depends on

P5 (app, feedback endpoint), P7 (gateway, tiers config, budgets).

## Inputs

For 1 entity: the `AccountDetail` the API already builds (signals,
evidence, scores, peer group, profile) plus the peer-group medians of
exposure and each fact (computed once per bundle in export; add
`peer_stats.parquet` to the bundle: peer_group, n, median exposure,
median fact_a..d).

## Outputs

```
sis/reportcard/build.py     build_findings(detail, peer_stats) -> list[Finding]: deterministic. 1 Finding per
                            fired signal with contribution > 0, ordered by contribution; each with headline
                            (from a SIGNAL_HEADLINES dict, templated with the value, e.g. "Certificate expired
                            on {date}", "{n} remote-admin services reachable"), the evidence rows, and the peer
                            comparison sentence ("Higher than {pct} percent of {n} similar businesses in {country}").
sis/reportcard/explain.py   explain(findings) -> list[Explanation(signal_id, what_it_means, what_to_do)]
                            via gateway.call(task='reportcard', ...). PROMPT_VERSION = "reportcard-1.0". System prompt rules: use only the
                            provided findings; refer to each by its signal_id; do not name any product, CVE,
                            number, vendor or date that is not in the input; 2 sentences each, <= 220 chars each,
                            plain language for a business owner, no fear language.
sis/reportcard/check.py     faithfulness(findings, explanations) -> CheckResult(passed, violations):
                            deterministic. Extract from the output: every CVE pattern, every integer >= 10,
                            every capitalised token sequence of 2+ words, every year; each must appear in the
                            input text of the same finding (case-insensitive) or in an allow-list of generic
                            terms (config/reportcard_allowlist.txt: e.g. "TLS", "HTTPS", "certificate",
                            "firewall"). Any violation -> fail -> 1 retry with the violations appended -> if
                            still failing, the card ships without explanations for those findings and says
                            "explanation withheld (failed faithfulness check)".
sis/reportcard/render.py    Jinja2 template reportcard.html + print.css. Sections: cover (name, segment,
                            exposure vs peer median, date, bundle version), findings (headline, what it
                            means, what to do, evidence table), protection present, "what this report is
                            based on" (1 paragraph: scan date, that it is observed-from-outside data, that
                            vulnerabilities are version-inferred unless marked verified, that nothing was
                            scanned by us).
sis/api/routes.py           POST /api/accounts/{id}/reportcard -> generates (or returns cached by evidence hash),
                            persists to $SIS_BUNDLE_DIR/report_cards/<id>.json and <id>.html; GET returns it.
                            The detail page's "Mark prospect" now also triggers generation and links the card.
evals/reportcard/judge.py   runs 50 cards (seed 31, from top 2,000 untouched) through a judge prompt via
                            gateway.call(task='judge', ...) (reasoning tier, different family from mid): for each explanation score faithful 0..2, specific 0..2,
                            readable 0..2 with 1-line rationale; writes results.json.
evals/reportcard/human.jsonl  the builder's scores for 30 of the same 50 on the same rubric, done before
                            looking at the judge output.
docs/REPORTCARD_REPORT.md
tests/test_reportcard.py
```

## Steps

1. **peer_stats** in export (small change to P5's bundle).
2. **Deterministic card** first, with no LLM, rendered end to end. Verify
   on 5 accounts by eye that headlines and peer sentences are correct.
3. **Explanations** via the client with the schema
   `Explanations(items: list[Explanation])`. Cache key includes the
   evidence hash so a changed bundle regenerates.
4. **Faithfulness check** as specified. Write the allow-list by running
   the check on 20 cards and reviewing every violation: generic security
   words go into the allow-list; anything that is a real fabrication
   stays a violation. Record how many of the 20 had real fabrications
   before the prompt was tightened.
5. **Judge eval** on 50; **human scoring** on 30 of them first. Report
   mean per rubric dimension for judge and human, and agreement (exact
   match rate and within-1 rate per dimension). If judge-human agreement
   on `faithful` is under 0.8 within-1, say the judge is not trustworthy
   for that dimension and rely on the deterministic check instead.
6. **Cost**: per card input and output tokens and USD from `llm_calls`;
   mean and p95 over the 50. Stay inside the mid and reasoning tier
   budgets; if the 50-card judge run would exceed the reasoning budget,
   stop and report the projection so the human can top up. Do not judge
   fewer than 50.
7. **Report** `docs/REPORTCARD_REPORT.md` with all of the above, 3 full
   example cards (1 untouched, 1 displace, 1 that had a withheld
   explanation), and the paragraph on why no scanning or web research is
   done. Copy cost per card and the faithfulness pass rate into DESIGN.md
   section 7.2.

## Does NOT do

- No scanning of the prospect, no fetching of their website, no web
  search, no external data. Inputs are our evidence only.
- No outreach email text.
- No remediation instructions beyond 1 generic "what to do" sentence per
  finding; this is a conversation opener, not a security assessment, and
  the card's footer says so.
- No regeneration for unchanged evidence.
