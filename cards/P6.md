# P6: Multi-file delta and change detection

Model: Sonnet 5.5. Day 4. This is the "right now" the single file cannot
give, proven on a synthetic second file and stated as a simulation.

## Goal

`uv run sis delta <from_file_id> <to_file_id>` writes `entity_history`
and `events` per DATA_MODEL.md section 4. `uv run sis synth <file_id>
--seed N` manufactures a second delivery by perturbing the real one in
known ways, so the delta can be tested against a known answer. Events
flow into the serve bundle and the detail page's "Changes" section.

## Read first

DESIGN.md sections 1 (point 5), 8, 12. DATA_MODEL.md section 4.
findings/06_relationships.md temporal section.

## Depends on

P3 (scores for both files). P5 for display (events table already has a
slot in the bundle).

## Inputs

2 ingested, resolved and scored files. For the submission, file A is
the real delivery and file B is the synthetic one.

## Outputs

```
sis/delta/synth.py          synth(file_id, seed) -> new raw zstd JSONL at $SIS_DATA/synth/<seed>.jsonl.zst
                            built by streaming the real Parquet back out as JSON? No: by streaming the
                            original raw file and applying perturbations line by line (keeps full fidelity).
                            Writes $SIS_DATA/synth/<seed>_truth.json: the exact list of perturbations applied.

sis/delta/sql/*.sql

$SIS_DATA/history/entity_history.parquet, $SIS_DATA/history/events.parquet
docs/DELTA_REPORT_<from>_<to>.md
tests/test_delta.py
```

## Steps

1. **Perturbations** (each applied to a seeded random subset of banners
   belonging to active entities; subset sizes are parameters with these
   defaults):
   - `drop_banner`: remove 2 percent of banners entirely (services gone)
   - `new_banner`: duplicate 1 percent of banners with a new `_shodan.id`,
     a port changed to 2222 or 8443, and `timestamp` shifted +30 days
     (services new)
   - `expire_cert`: for 1 percent of TLS banners, set `ssl.cert.expires`
     to 10 days before the new timestamp and `cert.expired` true
   - `remove_waf`: for 1 percent of banners with `http.waf`, delete the
     `http.waf` key
   - `add_waf`: for 1 percent of http banners without waf, set
     `http.waf = 'Cloudflare (Cloudflare Inc.)'`
   - `add_vuln`: for 0.5 percent of banners with cpe23, add 1 synthetic
     CVE `CVE-2099-00001` with cvss 9.8, verified false, kev absent
   - every surviving banner: `timestamp` shifted +30 days, `_shodan.id`
     unchanged (same observation id is acceptable for the simulation;
     state this)
   Write the truth file listing every affected `_shodan.id` and entity
   key_value per perturbation.
2. **Run the pipeline** on the synthetic file: ingest, resolve, score.
   It must pass through P1 as a distinct `file_id` (it will, the bytes
   differ).
3. **Diff** between consecutive files, at entity grain, using `current`
   tables and the 2 per-file tables:
   - `entity_new` / `entity_gone`: in 1 file's active entities and not
     the other's
   - `service_new` / `service_gone`: (entity, ip:port) sets differ
   - `signal_appeared` / `signal_cleared`: (entity, signal_id) sets differ
     for flag signals; for count signals, value crossed from 0 to >0 or
     back
   - `cert_expired_since`: `B_expired` 0 -> 1
   - `protection_removed` / `protection_added`: any D signal 1 -> 0 or 0 -> 1
   - `exposure_up` / `exposure_down`: absolute change >= 10
   - `segment_changed`
   Severity: 3 for protection_removed, cert_expired_since, service_new
   on an admin module, signal_appeared for A_eol or A_inferred_cves; 2
   for other appeared/new; 1 for the rest.
4. **History**: append both files' entity+score rows to
   `entity_history.parquet` (idempotent: delete rows for that file_id
   first).
5. **Verify against truth**: for each perturbation type, recall = events
   detected for perturbed entities / perturbed entities, and precision =
   events of that type on perturbed entities / all events of that type.
   Note which perturbations cannot map 1:1 to an event (a dropped banner
   on an entity with 2 banners on the same ip:port produces no
   `service_gone`) and account for them in the report, not by lowering
   the bar.
6. **Bundle**: `sis export` now includes `events` for the latest pair;
   the P5 detail page shows them. The accounts page gets 1 extra sort,
   `recent_change` (max severity event in the latest delta, then priority).
7. **Report** `docs/DELTA_REPORT_<from>_<to>.md`: perturbation counts,
   event counts by type, precision and recall per type, 10 example events
   with their evidence, wall time of the diff, and a paragraph stating
   that the second file is synthetic and what a real second delivery
   would add (re-observation gaps, genuinely new entities).
8. Copy the diff wall time into DESIGN.md section 8.

## Acceptance tests

```
uv run pytest tests/test_delta.py -q
  test_synth_truth_counts:      perturbation counts in truth file match the requested percentages within 1 entity
  test_diff_detects_removed_waf: 3-entity synthetic case -> exactly 1 protection_removed
  test_diff_idempotent:          running diff twice -> same events.parquet bytes
  test_event_id_stable
uv run sis synth <file_id> --seed 42
uv run sis ingest $SIS_DATA/synth/42.jsonl.zst && uv run sis resolve <id_b> && uv run sis score <id_b>
uv run sis delta <id_a> <id_b>
  DELTA_REPORT shows recall >= 0.95 for remove_waf, expire_cert, add_vuln; >= 0.90 for drop_banner/new_banner
  (if lower, the report explains each miss category; the card is done when every miss is explained)
```

## Does NOT do

- No scheduling, queueing or multi-worker orchestration (DESIGN 8).
- No alerts or notifications.
- No attempt to pass the synthetic file off as real: every report and the
  UI "Changes" header say "simulated second delivery".
- Does not re-observe-dedupe across more than 2 files (3+ file windows are
  described in DESIGN 8, point 5, not built).
