## The 3 defects and the architect's rulings

### Defect 1: hosting providers rank at the top (P3 finding)

22 of the top 100 and 193 of the top 1,000 are OVH per-/24 reverse-DNS
zones such as `ip-15-235-134.net`; 45 of the top 100 have hosting-like
names. Each covers under 50 IPs, so P2 keeps it as a customer, but it
aggregates many unrelated tenants' servers. 6,640 active entities have an
`ip-a-b-c.` key.

Ruling: these are operators. 3 rules, applied in P2 step 3 (operator
list), in this order:

1. **Template-zone rule.** A domain-kind key is an operator when the
   registered domain itself encodes an IP fragment: regex, case
   insensitive, on `key_value`:
   `^(ip|host|static|dyn|dynamic|rev|ptr|srv|vps|cust|customer|node|server|pool|cpe)[-.]?\d{1,3}([-.]\d{1,3}){1,3}\.` 
   or `^\d{1,3}([-.]\d{1,3}){2,3}\.`. Record the count matched.
2. **Hostname-template rule.** For every domain-kind key with
   `n_ips >= 10`: compute the share of its distinct hostnames whose first
   label contains 2 or more digit groups (regex `\d+\D+\d+`) or equals an
   IP with dots replaced. If that share `>= 0.8`, operator. This catches
   `hostinguk.net`-style zones whose hostnames are `server123.hostinguk.net`.
   Record the count matched and print the 30 largest by n_banners to the
   report; the builder reads them and reverts any that is plainly a
   single business (expected: none).
3. **Hand list.** Add to the seed block of `config/operator_domains.txt`
   every hosting-like name among the current top 100 by priority that
   rules 1 and 2 did not catch. Write each with a trailing comment
   `# hosting, top-100 eyeball P3.1`. The P3 report already names
   hostinguk.net, liquidweb.com, prioritycolo.com; check the full 100.

Both rules are parameters in `config/resolve.yaml` (new file: regexes,
`template_min_ips: 10`, `template_share: 0.8`), with a 1-line comment
each on why. Add tests: 6 keys that must match rule 1, 6 that must not
(`ip-cam-shop.com` must NOT match: the regex requires digit groups);
rule 2 on a synthetic 12-IP entity with 10 of 12 templated hostnames
(operator) and 7 of 12 (not).

### Defect 2: `low_surface` holds tested positives at the same rate as `untouched` (P4 finding 1)

Entities with a provider-tested vulnerability are being cut to half
score because the prerequisite definition is too narrow. The tests that
produce `opts_vulns` run on probes whose banners can have `data_len = 0`,
so `C_admin_services` (which requires a payload) misses them, and
`C_live_web` only sees http 200.

Ruling: the prerequisite means "something of theirs answered the
internet". Add 1 flag signal to the catalogue:

```
| C_any_service | C | 0/1 | any non-edge banner of the entity with data_len > 0, OR any non-edge banner with module not in ('auto') | DATA_MODEL 3.1 addition, P3.1 |
```

and widen the prerequisite in `config/scoring.yaml`:

```
prerequisite = C_live_web or C_admin_services > 0 or C_asset_tags > 0 or C_any_service
```

`C_any_service` has weight 0 in `fact_c` (it is a gate, not a score).
The multipliers do not change: `low_surface` at 0.5 is right once it
truly means "nothing of theirs answered". Record the segment counts
before and after.

### Defect 3: labels count edge banners that scoring ignores (P4 finding 5)

1,192 kev-positive entities have kev only on CDN or WAF edge banners.
That is the WAF vendor's CVE, not the tenant's, and facts A to C already
skip those banners.

Ruling: labels use the same banner scope as scoring. In
`sis/evaluate/sql/01_labels.sql`, exclude edge banners (same predicate as
P3's edge rule, from 1 shared SQL fragment or Python constant so the 2
cannot drift) for `label_kev`, `label_verified`, `label_heartbleed`,
`label_opts_vulns`, `label_ransomware`. `label_has_vendor` keeps edge
banners, since that is where the vendor shows. Report the label counts
before and after.
