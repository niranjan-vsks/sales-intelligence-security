# P5.1: UI readability pass and overview dashboard

Model: Sonnet 5.5. Half a day. Runs after P6 lands so the Changes
section is part of the design. Load these skills before writing any
template or CSS: `ui-ux-pro-max`, `impeccable`, `design-taste-frontend`,
`dataviz`. Use Playwright (`mcp__playwright__*`) for the walk and the
screenshots.

## Goal

A salesperson opens an account and knows in 5 seconds why it ranks where
it does. The list page scans. An overview page shows the shape of the
book of accounts. Dark theme by default, light theme working. No
framework, no build step, no animation beyond a 150 ms transition on
hover and expand. Every number on every page comes from the existing API
and bundle; this card adds no computation.

## Design rules

- **Palette.** Dark default: near-black background (not pure black),
  1 surface tone for cards, 1 border tone, high-contrast text, 1 accent
  used for the primary action and the exposure bar, 4 muted fact colours
  for A to D that stay distinguishable to colour-blind readers, and the
  4 segment colours: untouched = accent, partially covered = amber,
  displace = violet, low surface = grey. Light theme derives from the
  same tokens. Define every colour as a CSS variable on `:root`, redefine
  under `[data-theme="light"]`. Theme toggle in the header, persisted in
  localStorage. No company's brand colours or logo.
- **Type.** System font stack. 1 size scale (12, 14, 16, 20, 28). Numbers
  in tabular figures. Signal ids never appear outside a collapsed
  "Technical details" block.
- **Layout.** Max width 1,200 px, 16 px gutter, works at 390 px wide
  without horizontal scroll. Sticky header with: product name, nav
  (Overview, Accounts, About), theme toggle, bundle version.
- **Plain labels.** A `SIGNAL_LABELS` dict (exists or is created in
  `sis/api/labels.py`) maps every signal id to a short plain sentence
  template with the value substituted, e.g. `A_inferred_cves` ->
  "{n} known vulnerabilities inferred from software versions",
  `B_expired` -> "A TLS certificate has expired", `C_admin_services` ->
  "{n} remote-admin or database services reachable from the internet",
  `D_waf` -> "Behind {vendor}". Facts: A "Visibly old software",
  B "Neglected certificates", C "Exposed surface", D "Protection present".
  Segments: "Untouched", "Partially covered", "Has a vendor (displace)",
  "Low visible surface".

## Pages

### 1. Overview (`/`), new. Accounts list moves to `/accounts`.

Top row, 4 stat tiles: total active accounts; untouched; has a vendor;
changed since last delivery (events count, with "simulated" tag when
`meta.delta.simulated`). Each tile is a link to the filtered list.

Second row, 2 panels:
- Segment split: horizontal bar, 4 segments, counts and percent,
  clickable.
- Exposure distribution: histogram of exposure in 10 buckets, inline
  SVG, hover shows count. Data: add `exposure_hist` (10 counts) to
  `/api/stats` computed by 1 DuckDB query at request time (it is 487,000
  rows; fine) and cached in app.state for the process lifetime.

Third row, 2 panels:
- Top countries: 10 bars, count, clickable to the filtered list.
- Most common reasons: top 8 signals by number of accounts firing them,
  plain labels, count. Data: add `signal_fire_counts` to `/api/stats`
  (1 query over signals.parquet, cached).

Fourth row: "Start here" list, the top 10 untouched accounts by
priority, as compact cards: name, exposure bar, 1-line top reason,
country. Links to detail.

### 2. Accounts (`/accounts`)

Filter bar as a single row: search box, segment chips (toggle, multi),
country select, min exposure slider or input, sort select. Chips show
counts. Filters update the table via htmx as today.

Rows: name (link), segment badge, exposure bar with the number inside,
priority, top reason in words, country, n services, industry if present,
a small "changed" dot when the account has an event in the latest delta.
50 per page, page controls top and bottom, "showing x to y of n".

### 3. Account detail (`/accounts/{id}`)

Header card: name; segment badge; exposure as a large number with a bar;
rank overall and rank in segment; country; peer group in words ("Compared
with 2,314 accounts in DE with 2 to 3 services"); operator ("Hosted at
OVH"); industry and description when present; "changed" tag with the
highest-severity event if any.

Fact panel: 4 rows, A to D, each: plain name, bar 0 to 1, score to 2
decimals, 1 short sentence of what the fact means (fixed text).

Why panel: the top signals from `explain.py`, 1 line each in plain
words with the contribution on the right, max 5. Under each line a
"Show evidence (n)" toggle that expands the evidence rows for that
signal: ip, port, module, observed time, and the snippet in a monospace
block with wrapping. Collapsed by default. Evidence for signals outside
the top 5 lives under 1 "All signals (n)" toggle at the bottom of the
panel.

Protection panel: the D signals present, each with the vendor or header
value, in plain words; if none, "No security product or edge protection
observed".

Changes panel: only when events exist. Each event: severity dot, plain
sentence ("A TLS certificate expired since the last delivery",
"Protection by Cloudflare was removed"), subject, date. "Simulated second
delivery" note stays, as 1 muted line, when applicable.

Actions: "Mark as prospect" and "Not a fit" as 2 buttons in the header
card, confirmation swaps in place as today.

Technical details: 1 collapsed block at the end with signal ids, raw
values, peer percentiles, entity id, key kind, bundle and scoring
version.

### 4. About (`/about`)

Unchanged content, restyled with the same tokens, max width 760 px for
reading.

## Steps

1. Load the 4 skills. Write `sis/api/static/tokens.css` (variables, both
   themes) and `app.css` (components). Delete the old 50-line CSS.
2. `labels.py` with every signal, fact, segment and event type label.
   Test: every id in the catalogue and every event type has a label.
3. Extend `/api/stats` with `exposure_hist` and `signal_fire_counts`,
   cached. Tests for shape.
4. Templates: base, overview, accounts, _rows, account, about. htmx
   stays. No new JS beyond the theme toggle and the expand toggles
   (native `<details>` is acceptable and preferred).
5. Walk with Playwright at 1,280 px and 390 px, dark and light: overview,
   accounts with 2 filters applied, a detail page for 1 untouched and 1
   displace account, expand evidence, mark prospect, about. Save
   screenshots to `docs/ui/` (8 to 12 PNGs) and reference them in
   `docs/UI_REPORT.md` with 1 line each on what the page shows.
6. Console must be clean on every page. Lighthouse accessibility score
   from Playwright or the Chrome CLI at or above 90 on overview and
   detail; record the number.
7. Export is unchanged. Rebuild the image, redeploy per docs/DEPLOY.md
   (copy feedback.jsonl out first), run the live smoke, update the
   screenshots section of DESIGN.md 11 with 1 sentence: UI kept minimal
   on purpose, 1 readability pass after the first live walk, no
   framework.

## Does NOT do

- No new computation outside the 2 stats additions. No change to
  scoring, bundle or evaluation.
- No charts library, no React, no Tailwind, no icon font (inline SVG
  only).
- No chatbot, no homepage marketing copy, no brand colours or logos.
- No email drafting, no CSV export.
